# 界面尺寸：按屏幕缩放（2026-11-01）

## 起因

用户在 14 英寸 MacBook Pro 上开发，对现在的观感满意，但在 16 英寸笔记本上“有些元素过大、不够精致”，在 18、24、27、32 英寸上更明显。

调研发现，用户这台 14 英寸用的是“更多空间”：`screen` 为 1800×1169、DPR 2，约每英寸 151 个 CSS px。14 英寸与 16 英寸 MacBook 的默认缩放（1512 / 1728）都约 127，常见外接屏约 70–110（27 英寸 4K 在 macOS 默认的 1920×1080 下约 82，24 英寸 1080p 约 92）。CSS px 数相同时，这些屏幕上的元素实际大 20–80%。扩展自身的断点在 1512 与 1728 之间几乎没有变化（Dock 宽版从 1024 起就生效），所以问题不在断点，而在每个 CSS px 的物理大小。

## 用户的决定

- 基准是用户现在的 14 英寸（更多空间）。代价：14 英寸用默认缩放（1512×982）的人也会缩到 0.875。
- 不追求精确 1:1，取整到像素对齐的档位，保证清晰。
- 外接屏按观看距离补偿。
- 文字缩得更少。
- 不做完全线性缩放，以观看效果为准。

## 推断屏幕

浏览器拿不到英寸，只有 `screen.width/height`（CSS px）、`devicePixelRatio` 与平台。`utils/uiScale.ts` 依次：

1. macOS：缩放模式按 2x 绘制，backing store 的一半就是“看起来像”的尺寸（不受页面缩放影响）。按内建屏与 Apple 显示器的精确模式表查面板对角线（13.3、13.6、14.2、15.4、16、16.2 英寸 MacBook，24 英寸 iMac，32 英寸 Pro Display XDR）。比较时允许 1 点误差，因为页面缩放会把 `screen` 取整。
2. 非 macOS 且 DPR ≥ 1.25、宽度 ≤ 1920：笔记本。Windows / Linux 的推荐缩放让笔记本稳定在约每英寸 120 CSS px，直接取这个值。
3. 其他：按物理分辨率查常见显示器的对角线（1080p / 1200p 为 24 英寸，1440p 与 4K、5K 为 27 英寸，3440×1440 为 34 英寸，6016×3384 为 32 英寸……），逻辑宽度取该面板的默认系统缩放（Windows：4K 为 150%、5K / 6K 为 200%，其余 100%；macOS：高度 ≥ 2160 为 2x），不取当前 DPR，所以页面缩放和用户自己调大的系统缩放不会被抵消。
4. 认不出的屏幕保持 1，不猜。

密度乘观看距离系数：16 英寸及以下为 1（约 50cm），之后线性增加到 32 英寸的 1.5（约 75cm）。目标因子 = 密度 / 151，夹在 0.75–1，从不放大。

## 取整

因子只取“4px 网格正好是整数个物理像素”的档位：`n / (4 × DPR)`。2x 屏为 1、0.875、0.75，1x 屏为 1、0.75，1.5x 为 1、0.833、0.667，1.25x 为 1、0.8、0.6。取最近的档位，1 始终是候选（页面缩放让 4 × DPR 不是整数时也能回到 1）。每个长度 token 再用 CSS `round()` 取整到 `--bew-ui-pixel`（1 / DPR px）。

## 生效方式

- 唯一的因子 `--bew-ui-scale`，以及 `--bew-ui-pixel`。`composables/useUiScale.ts` 的 `setupUiScale` 在内容脚本启动时（启动遮罩之前）解析一次，之后只在窗口换屏（`screen` 的 `change` 事件）、DPR 或页面缩放变化（`resolution` 媒体查询）与设置变化时重算。只在值改变时写 html 与 `#bewly` 宿主，等于 1 时不写，所以基准屏上没有任何新的样式写入。
- 布局长度用 `#{ui(Npx)}`：间距、圆角、控件高度、Dock 项、顶栏高度与主控件、侧栏与通知列宽度上下限、弹窗与浮层宽度、日期选择器、首页搜索区、视频卡片最小宽度。
- 文字与紧挨文字的图标、品牌 Logo 用一半的因子：`--bew-ui-text-scale = (1 + 因子) / 2`。字号乘在 `--bew-font-scale` 与界面基础字号之上，系统与浏览器的文字偏好不被吃掉。0.875 时正文 13px → 12.19px，0.75 时约 11.4px。
- 不缩：页面与内容的最大宽度（2280、1920、抽屉 1400）、24px 最小点击目标、发丝线（仍是一个物理像素）、模糊、阴影、动画时长、视口断点（媒体查询不能用变量，且它们描述的是窗口宽度）。
- UnoCSS 的 rem 转换里，没有对应间距 token 的值也走同样的 `round(… * var(--bew-ui-scale), var(--bew-ui-pixel))`。
- 用 `ui()` / `ui-text()` 的 69 个 token 注册为 `<length>`（`_uiScale.scss` 的 `$lengths`，经 `main.scss` 的 `uiScale.global` 输出 `@property`）。不注册时它们的计算值是未求值的 `round(...)` 字符串，约十处 `parseFloat(getPropertyValue(...))`（评论树弯角、选中行滚动余量、播放页几何、MAIN world 的评论桥等）会得到 NaN，即使因子为 1 也会出错。注册后计算值与改动前逐字相同。
- JS 里与 token 对应的长度经 `uiPx(设计 px)` 换算（与 CSS 同样取整，在 computed 里随因子更新）：视频网格列数与横向封面上限（`VideoCardGrid`、`Ranking`）、观看历史的卡片间距 / 行距 / 估高、历史行与关注侧栏的虚拟窗口间距、Dock 的适配与收起外壳、首页搜索区高度与吸顶位置、首页与独立搜索页的 Logo。列表布局键带上因子，因子变化时重新测量；`invalidateViewportGeometry` 也随之触发。
- 设置“界面尺寸”（`interfaceSize`）在“视觉风格 → 高级”：自动 / 紧凑（比 1 小一档）/ 标准（1）/ 宽松（大一档），说明里显示当前百分比。它属于一台设备，列入 `LOCAL_ONLY_SETTINGS_FIELDS`，不云同步。

## 验证

- `pnpm verify:ui-scale`（已加入 `pnpm test`）：各类屏幕的因子、基准屏在 50%–175% 页面缩放下保持 1、所有档位落在物理像素上、JS 与 CSS 取整一致、`$lengths` 与 `ui()` token 一致、文字因子组合、发丝线与 24px 目标不缩。
- 在用户的 14 英寸上实测：自动得到 1，html 与宿主没有写入，`--bew-space-4`、`--bew-control-height`、`--bew-dock-item-height`、`--bew-video-card-min-width`、正文字号均为改动前的 16 / 36 / 54 / 320 / 13px。选“紧凑”后分别为 14 / 31.5 / 47.5 / 280px、正文 12.19px，图标 16 → 15px，24px 目标与 0.5px 发丝线不变。

## 已知限制

- 第三方显示器的尺寸只能按分辨率猜：32 英寸 4K @150% 会被当成 27 英寸（得 1，实际约 0.83），用 1080p 的 15.6 英寸笔记本在 100% 下会被当成 24 英寸显示器。设置里的“紧凑 / 标准”用来纠正。
- Windows 上页面缩放与系统缩放都表现为 DPR，无法区分。显示器按面板的默认缩放估算，不受影响；笔记本按固定密度估算，但缩小页面到宽度超过 1920 或 DPR 低于 1.25 时会被归为显示器。macOS 按 2x backing store 归一，不受页面缩放影响。
- 组件里约 640 处字面量 px（多数在原生页适配）不随因子缩放；B 站原生页面自己的元素也不缩放，只有经 token 的适配样式缩放（与 `--bew-font-scale` 的既有做法一致）。
- 开发时，清单注入的 `style.css`（文档级 token 与 `@property`）只在重新加载扩展后更新；只刷新页面时 Shadow DOM 内是新的，文档级仍是旧的。
- 1x 屏上只有 1 与 0.75 两档。这是用户“像素对齐优先”的取舍。
