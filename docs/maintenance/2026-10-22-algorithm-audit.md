# 2026-10-22 算法与实现性能审查

本文记录优化前的审查结果。用户批准后的落地状态与复测见 [实施记录](2026-10-22-performance-implementation.md)。

## 结论与范围

不能认定项目的所有算法和实现都是性能最优。视频网格的高度索引、增量动态布局、请求合并和媒体资源归属已经有良好基础；通知长列表、用户过滤规则、收藏搜索和私信历史结果处理仍有具体优化空间。

本次以工具链升级后的工作区为准。源目录有 775 个 TS/Vue 文件，约 15.9 万行；使用全局高成本模式检索，再深读关键调用链，覆盖列表/几何、过滤/搜索、评论树、缓存/请求、设置同步与媒体调度。不是对每一行代码的最优性证明。没有修改产品代码，没有操作浏览器，没有以 Node 测试代替浏览器布局、GPU 或真实 API 性能。

数据见 [基准结果](evidence/2026-10-22-algorithm-benchmarks.json)。普通计时使用项目 Node 26.12.1，预热后取 7 次中位数；合成数据仅用来比较方法和扩展趋势。函数通过现有 sourceFunctionHarness 提取当前源码运行。候选实现只用于实验，未落入生产代码。索引方案的查询计时不包含一次性索引构建成本，须同时考虑更新与内存成本。

[主要基准脚本存档](evidence/2026-10-22-algorithm-benchmark.mts.txt) 对应本次优化前的源码；其中私有函数与旧组件在实施后已有调整。当前实现使用 `scripts/verify-performance-implementation.mjs` 回归。60 项过滤批次和带终止预算的正则实验是补充测量，分别列在结果 JSON 的 `filterBatch` 与 `regexBudgetProbe` 中。

## 建议优先处理

### 1. 高优先：任意过滤正则在 UI 线程同步执行

- `src/utils/filterRules.ts:32–45` 仅验证能否构造 RegExp；`src/composables/useFilter.ts:75–97` 同步调用 `.test()`。
- 规则导入允许最多 2,000 条、每条 512 字符。这些上限不能限制回溯匹配的计算量。
- 隔离 Worker 实验：合法模式 `^(a+)+$`、项目相同的 `i` 标志，对重复字符加不匹配后缀，18 个重复字符耗时约 16.8ms，22 个约 262.9ms，26 个在 500ms 预算到达后终止。该实验是 Node 结果，不是用户 Chrome 的冻结时长；源码路径与可阻塞特征已确认。
- 优先为正则建立可终止的执行边界和预算；若改用保证线性复杂度的引擎，必须先定义回溯引用、前后查找等现有语法的兼容策略。单纯减少规则数量、给主线程外面包一个 timeout 或只做语法合法性检查不能可靠中断正在执行的正则。
- 资料：[V8 对灾难性回溯与非回溯引擎的说明](https://v8.dev/blog/non-backtracking-regexp)。该资料用于解释机制，当前环境耗时来自本次实验。

### 2. 高优先：通知长列表没有窗口化，布局工作随已加载总数增长

- `src/contentScripts/views/Notifications/components/NativeNotificationFeed.vue:458–469` 为 `state.items` 每项保留组件和 DOM。
- `composables/useNotificationFeed.ts:243–265` 每页重建全部已加载 ID 的 Set，再持续追加；没有窗口渲染层。
- `src/components/MasonryGrid.vue:44–78` 虽然只测量 dirty 项高度，仍对全部子项重新分配列位置；`106–132` 每次组件更新还会遍历所有子项维护观察器。
- 直接执行实际 layout 函数，追加 20 项：已有 100 / 1,000 / 5,000 项时，属性检查分别为 240 / 2,040 / 10,040 次，保留 DOM 分别为 120 / 1,020 / 5,020。高度读取始终只有 20 次，说明已做测量复用，但总遍历与 DOM 数仍线性增长。实验没有测量浏览器布局耗时。
- 优先复用已有窗口化/高度索引能力，保留 DOM 顺序、阅读锚点、焦点与未读语义；分页去重改为按会话维护增量索引。单纯把找最短列改为堆不会解决主要成本，因为列数很少，真正增长的是全部历史条目。

### 3. 中优先：普通过滤规则有可避免的重复字符串转换

- `src/composables/useFilter.ts:78` 在每个关键词的 `.some()` 回调中对同一个标题重新 `toUpperCase()`。
- `:96` 对用户名做数组 `.includes()`，每条视频最多比较两种用户字段。
- 2,000 条不命中的普通规则、60 条标题：当前约 20.78ms，每个标题只规范化一次约 2.51ms；1,000 条标题约 335.70ms → 29.89ms。
- 同样规则下，1,000 次用户名匹配约 1.88ms，设置更新时构建 Set 后约 0.09ms。Set 的构建成本应在设置变更时支付，不应每条视频重建。
- 这是大量规则条件下的合成比较。首页通常分批过滤，不应把 1,000 条基准的耗时直接当成每次首页请求耗时。
- 先把标题规范化移到逐项匹配前，把精确用户名规则编译成 Set；规则规模进一步增大时再比较多模式匹配算法的额外内存和维护成本。

### 4. 中优先：收藏搜索重复规范化查询与不变的内容

- `src/contentScripts/views/Favorites/favoriteSearch.ts:2–6` 每个候选都重新做查询 NFKC/大小写转换和分词，也重新转换内容；空查询仍构建全文字符串。
- `useFavoritesData.ts:96–102` 的 computed 在查询或列表变更时再次逐项调用。
- 10,000 项、两个查询词：当前约 7.56ms，复用规范化文本索引后查询约 0.45ms；空查询当前约 6.33ms。后者可直接返回原列表。索引计时不含构建和失效维护。
- 建议每次查询仅编译一次；按条目稳定身份/内容版本复用文本，编辑或追加时只更新变更项。正常小收藏列表成本很低，不宜为此先引入重量级全文搜索依赖。

### 5. 中低优先：私信历史搜索每页排序整个深响应式结果集

- `src/contentScripts/views/Notifications/whisper/usePrivateHistorySearch.ts:36–39, 182–200` 的 results 是深响应式数组；每页结束都会排序全部累计结果，即使本页没有命中。
- 当前结果上限 2,000，单页 20 条且请求有 200ms 间隔。对已排序的 2,000 项，纯数组排序约 0.04ms，Vue reactive 数组约 1.81ms；200 项约 0.01ms / 0.18ms。此比较仅隔离排序及代理开销，不含 Vue 视图更新。
- 无新增匹配时跳过排序；有新增时按时间有序合并，并考虑 shallow 数组整体替换。网络等待仍可能占主要耗时，因此优先级低于通知窗口化和大规则过滤。

## 可以保留的方法

| 路径 | 已确认的设计 | 判断 |
| --- | --- | --- |
| `utils/cardRowMetrics.ts` | Fenwick 树 O(n) 初始化、O(log n) 高度更新/定位 | 合适；20,000 次定位从 1,000 行增至 100,000 行仅约 2.53ms → 2.81ms |
| `utils/momentColumnIndex.ts`、`useMomentLayout.ts` | 稳定列增量追加、位置 Map、可见窗口计算；最多三列 | 不必为找最短列引入堆；保留现有阅读稳定性 |
| `utils/viewportGeometry.ts` | 同一滚动容器的共享帧调度和同轮几何缓存 | 正确方向；实际浏览器强制布局需另测 |
| `utils/imageLoadQueue.ts` | 六并发、可见项预留两槽、几何版本缓存、隐藏页停止启动 | 不能只为吞吐盲目加并发；排序/数组队列是否值得换结构取决于实际待加载规模 |
| `utils/commentReplyPageCache.ts` | 线程/页/条目上限、同页请求合并、最后读者离开才取消 | 拷贝隔离是为了阻止原生 renderer 污染共享缓存，不应直接删除 |
| `background/stateConsumers.ts` | 按主题、活动文档、隐私上下文和版本发送 | 已避免无差别全标签页广播 |
| `composables/useSettingsStorage.ts` | 字段差分、同轮合并、共享未变化分支、后台写入协调 | 已比整份反复写入合理；deep watch 和比较大规则数组的实际交互成本仍应专项测量 |

## 低优先与待实测项

- `utils/commentTree.ts:48–64, 95–110` 对每个节点重复追溯祖先，链状最坏 O(n²)，即使视觉深度限制为 6 也不会减少前面的环检查。240 节点链约 1.47ms；1,000 / 3,000 节点约 23.95 / 212.90ms。当前增强缓存通常限制每线程 240 项，因此后两组是压力情形，不应据此声称日常评论会消耗数百毫秒。可在需要扩大上限时采用带状态缓存的线性环检测，并保留现有环断开和缺失父节点语义。
- Vite 内容脚本仍是 IIFE 单包；开发产物内能看到动态 import 转为 `Promise.resolve().then(...)` 和延迟模块初始化。异步页面挂载不等于代码拆包。新开发主包约 17.1MB，包含嵌入样式；需要在生产压缩产物上测量代码缓存、启动、解析和内存后再决定拆包方案，不能用开发包字节数推算首屏延迟。
- 正在播放的媒体解码、渐进模糊的 GPU 成本、实际滚动 INP/掉帧、字体/图片重排以及 B 站网络耗时，本次未做浏览器性能录制。产品要求的渐变模糊质量和交互语义是约束条件，减少层数并不自动构成“更优实现”。

## 建议顺序

先处理正则执行边界和通知窗口化；随后做普通过滤与收藏文本索引；再优化私信历史结果的无效排序。评论树和启动拆包在对应规模/实站性能证据支持后实施。每项优化应分别验证行为一致性、测量收益和资源清理，避免一次性改写所有共享层。
